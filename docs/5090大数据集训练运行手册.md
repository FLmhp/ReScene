# RTX 5090 大数据集训练运行手册

开发基线为 `codex/workbench-reliability` 的 `5f512e7`，已发布版本为 0.4.0。5090 关机期间可完成本地开发、隔离验收和实验准备。开机批次以累计通电 30 小时为上限，包含环境检查、运行、归档和 Worker 恢复。训练指逐场景优化 3D Gaussian，几何模型使用冻结的预训练权重。[工作台验收](../artifacts/test-runs/2026-11-18-workbench-reliability/report.md) · [0.4.0 发布验收](../artifacts/test-runs/2026-11-18-ui-v040/report.md)

## 0. 5090 关机期间的开发计划

首批交付约 5–8 人日，可并行准备客户端验收和 CPU 实验。以表中验收结果作为合并依据。

| 顺序 | 工作 | 交付与验收 |
|---|---|---|
| 1 · 1–2 人日 | 收口当前工作台分支。用隔离 PostgreSQL、测试 API 和已有 SPZ 完成四端回归。 | 四端检查登录、素材预览与删除、跨页选图、排队、取消与重试、结果浏览或跳转及下载。用测试 Worker 驱动阶段与结果，验证 Web/桌面 SSE 重连、Android/小程序恢复前台后的状态。记录提交、设备、步骤和关键截图，区分真实直传、模拟任务和历史场景。 |
| 2 · 1–2 人日 | 处理 OSS 与任务恢复的关键路径。 | 保留 PostgreSQL 单卡队列，补齐 OSS 上传/归档失败、过期回调、重复完成、排队取消和备份恢复用例。以已有 Worker 状态和日志补充队列等待、最后心跳、失败码和最近成功备份。发布前核对 OpenAPI、共享 Zod 契约和四端调用。 |
| 3 · 2–3 人日 | 改进实验准备、执行和结果校验。 | 增加 CPU 预检，冻结场景、源图 SHA-256 和验证划分，并从试验规格传递随机种子到几何和训练阶段。监督器具备批次预算、动态磁盘门槛和失败分类。成功产物先归档校验再清理，能在同一试验身份下恢复。用合成图、伪 CUDA 子进程和临时目录验证超时、空间不足、归档损坏与中止清理。 |
| 4 · 1 人日 | 准备 QUALITY 全局建图和 MV-DUSt3R+ 的实验入口。 | 用 CPU 小型 COLMAP 模型验证共同输出契约和投影，记录依赖、权重、许可证与显存待测项。QUALITY 实验使用锁定的 PyCOLMAP，MV-DUSt3R+ 使用独立环境。两者以实验规格启用。 |

验收时优先使用本地或已授权的隔离 OSS 前缀和客户端已配置的 HTTPS 地址。个人主体小程序按复制链接后在浏览器打开的实际路径验收。新版还需在真实 Worker 完成一条图片任务和一条视频任务，以补齐 GPU 到 OSS 和 Viewer 的整链路证据。发布按兼容 API 先于客户端的顺序，使用新版本与可回滚镜像；日常检查见 [开发与发布指南](../CONTRIBUTING.md)。

若 5090 继续关机，第二批优先做两项可离线验收的改进。其一，将现有 Worker 的不可解码、格式、模糊及重复提示前移到素材选择和提交任务的界面，用故障样例验证四端反馈；服务端继续校验原始对象。其二，把生产 API 兼容、角色/越权用例和备份恢复转成可重复执行的验收流程。训练中途续跑根据实际重跑成本立项，先验证 gsplat 能否一起恢复迭代号、优化器与增密状态。GLB、编辑工具和多 Worker 调度安排在当前交付链路验收之后。

复跑本地验收从仓库根目录执行 `.venv/Scripts/python.exe scripts/verify_offline.py --build-clients`。脚本创建独立 PostgreSQL 16 容器，完成类型、契约与角色回归，备份后在新数据库验证项目和角色权限，并构建四端。Windows 上 Web 与桌面浏览器场景使用 `scripts/verify_ui.py` 保存结果和截图。素材预检覆盖扩展名及文件头、图片解码和 96×96 缩略图。模糊与同批疑似重复可由用户确认继续；视频编解码和最终字节校验由 Worker 执行。

在控制服务器的 ReScene 部署目录可读取最老排队时间、Worker 心跳和近 24 小时失败码。队列年龄从当前进入 `QUEUED` 的更新时间计算。最新备份按生成时间检查，本地恢复演练另用独立数据库执行。

```bash
docker compose --env-file infra/.env -f infra/compose.yaml exec -T db \
  psql -qAt -v ON_ERROR_STOP=1 -U rescene -d rescene < infra/deploy/health_snapshot.sql
ls -1t infra/backups/rescene-*.dump | head -n 1
```

## 1. 环境、目录与容量

登录后核对实例 GPU 名称、实际总显存、驱动、CUDA runtime 和 PyTorch Compute Capability。确认 gsplat 扩展支持 `sm_120`，记录 VGGT 权重、gsplat 扩展文件、第三方源码、环境锁和 Git 提交的 SHA-256 或 Git SHA。重新使用克隆实例时，先核对挂载与私有运行环境，再检查 `/root/ReScene/workerctl status`。

| 位置 | 用途 | 上限或门槛 |
|---|---|---:|
| `/root/autodl-fs/rescene/datasets` | 下载包、许可、内容清单及真值包 | 45 GB |
| `/root/autodl-fs/rescene/runtime-bundles` | 离线安装包、模型与版本清单 | 20 GB |
| `/root/autodl-fs/rescene/experiments/<suite-id>` | 冻结计划、试验指标、选定产物 | 65 GB |
| `/root/autodl-fs/rescene/staging` | 下载临时文件、上传未完成归档 | 20 GB |
| `/root/autodl-tmp/rescene/large-scenes/<suite-id>` | 单场景解包、运行输出和临时缓存 | 开跑前可用 ≥10 GiB 且 ≥本次预计写入的 1.3 倍 |

ReScene 的共享盘预算合计 150 GB，账户额度为 200 GB。每批次先用 `mountpoint -q /root/autodl-fs` 验证确实挂载，再用 `findmnt --target /root/autodl-fs`、`df -h /root/autodl-fs /root/autodl-tmp` 和控制台实际配额确认空间。共享盘保留冷数据，本地盘只展开当前场景，阶段产物先写本地。估算缓冲包含解包、去畸变、COLMAP MVS 临时文件、Gaussian checkpoint 和最终 PLY/SPZ。挂载缺失、预测空间不足或任一哈希校验失败即停止本批次。

共享盘便于克隆实例间复用数据，热数据从本地盘读取。把可再下载的源文件保留成归档，避免同时积压解包版本。生产素材及交付产物仍由 OSS 管理。[AutoDL 文件存储说明](https://api.autodl.com/docs/fs/)

## 2. 数据与冻结清单

| 数据 | 开发组 | 留出组 | 用途 |
|---|---|---|---|
| Golden Kitchen | 固定历史清单 | 无 | 校验环境与三条路线，复测历史基线 |
| ETH3D Low-res many-view | `delivery_area` 室内、`playground` 室外 | `terrains` 室内、`forest` 室外 | 主实验。官方图像分别有 4×237、4×240、4×165、4×257 张 |
| Mip-NeRF 360 | `room`、`garden` | `counter`、`treehill` | 独立补充批次，检查高分辨率细节；使用条件与空间确认后再下载 |

ETH3D 按场景缓存官方去畸变图、标定、点云真值和遮挡包。已有同物理场景的历史版本归入开发组，包括不同相机或分辨率。冻结前核对仓库及共享盘上的场景历史。发现留出场景已用于选型时，按场景 ID 字典序选择同环境且从未调优的可用替代场景，并要求使用条款与所需真值齐备。缺室内或室外的独立证据时，将相关路线记为样本不足。共享盘只归档合规原图和真值。[ETH3D 官方数据](https://www.eth3d.net/datasets) · [Mip-NeRF 360 官方下载](https://jonbarron.info/mipnerf360/)

1. 每个下载包先写 `.partial`。校验发布方提供的摘要，再记录本次 SHA-256、字节数、下载 URL、使用条件和归档日期。通过后在同一挂载点原子改名。
2. 按时间戳、相机编号和相对路径稳定排序。多相机数据按采集时刻分组，在每段轮换相机。素材清单记录相对路径、哈希、相机、时间、尺寸和来源。开机前完成解码、EXIF、重复与尺寸检查。
3. 在 8 个等长时间段各选一个靠近段中部的合格视图，冻结每场景 8 张验证图和源图 ID。通过 `discover_images()` 的实际排序校验规格 `validation.sources`。Golden Kitchen 沿用原冻结清单。建图后验证任何一张目标图缺失都记作失败。
4. 生成嵌套的 64、80、160、250 帧子集，帧数均包含这 8 张验证图。先从其余合格图覆盖整条轨迹选 56 张，再从剩余帧均匀补入后续档位，平局按相对路径。CPU 预检要验证实际进入几何的源 ID、训练/验证划分与规格完全一致。预处理若丢帧，记录原因并在第一次跑基线前修订整组清单。冻结后按原清单评估。
5. 主实验沿用现有的光度留出协议。验证图可参与相机估计，从 Gaussian 优化图像集中留出，所有路线使用同一组验证图。几何评估使用独立标定与真值，按产物坐标对齐。少视图新模型另用全程留出的评测口径。

`scripts/freeze_manyview.py <按采集时间排序的平铺图像目录> <新输出目录>` 可在 CPU 上生成四个嵌套子集和 `frozen.json`。对 ETH3D 官方多相机目录，传入场景的 `images/` 并加 `--eth3d-rig`，保留相机编号、时间戳和原始标定文件所用的相对图像路径。将清单中对应子集填入试验规格，并设置 `profile`、`candidate_id`、`seed`、`environment_lock` 和 `environment_lock_sha256`。同步到 AutoDL 后仅重定位数据和锁文件路径，再用 `python scripts/route_experiments_v3.py <spec.json> --preflight` 核对实际筛选的源图。

## 3. 开机、运行与恢复

1. 开机前先确认维护窗口。开机后完成挂载、环境、配额、源哈希检查，确保只运行一个实验批次。等待活动任务结束，确认 Worker 为空闲的 `running drain=no`。以正常模式启动监督器，由它负责 drain、stop，并通过 `flock --close` 获取 `/root/ReScene/.gpu.lock`。发现外部 GPU 计算进程则暂停，忙闲判断以 compute PID 为准。
2. 每个批次使用独立的 `suite-id`，用 `RESCENE_DELIVERY_ROOT` 把工作目录指向本地数据盘。沿用 `scripts/route_experiments_v3.py` 的 JSON 单试验规格及 `scripts/supervise_route_experiments.py` 的 JSON 计划。每条规格显式写 `scene`、`scene_id`、`candidate_id`、`profile`、`frame_limit`、`validation.sources` 和 `overrides`。批次计划逐项列 `name`、`spec`、`repeat`。
3. 第一条正式试验前完成 §0 的运行器改动。每条试验以源图哈希、划分、配置、种子和环境锁识别。复用旧结果时校验相同身份及归档哈希。性能对照从同样的冷启动边界开始，恢复重跑单独记时。测得同场景基线前沿用监督器已有单次上限；测得后用近期有效耗时中位数的 1.5 倍估算，开跑前同时检查空间与本批次剩余时间。
4. 用 `nohup` 启动并记录 PID 与日志路径。每次只展开一个场景，CPU 使用 12 核上限，GPU 计时期间暂停 CPU 密集评测。OOM 或模型明确失败记入该配置失败率，现有的单次 OOM 降级另记诊断结果。同场景的其他独立配对可继续。挂载丢失、磁盘越线、锁异常或外部 GPU 进程则停批次。可确认的瞬时基础设施故障最多重跑一次，并保留原尝试。
5. 通电累计到第 28 小时停止开跑；每条试验的硬截止取已有单次上限和距收尾窗口的剩余时间两者中较小值。停止时只结束本次进程树，确认锁释放后恢复 Worker。记录 `drain=no`、心跳、待处理队列、运行环境摘要和剩余预算。

完成上述启动检查后，从 `ReScene` 根目录按实际批次名启动。`specs/plan.json` 的每条试验额外提供 `profile`、`expected_write_bytes` 和 `wall_estimate_seconds`。对保留模型的基线和最终候选在规格中设 `keep_artifacts: true`。缓存匹配数据库时提供 `matching_db` 和 `matching_db_sha256`，全局建图候选覆盖 `colmap_mapper: global`。续跑时保留规格及试验名，用 `resume: true` 显式接续；已完成试验会校验输入、配置和归档后跳过。

```bash
export RESCENE_DELIVERY_ROOT=/root/autodl-tmp/rescene/large-scenes/manyview-v1
export RESCENE_EXPERIMENT_ARCHIVE=/root/autodl-fs/rescene/experiments/manyview-v1
# trial_deadline 为扣除此前累计通电时长后、进入最后两小时收尾窗口的 Unix 时间戳。
nohup .venv/bin/python -u scripts/supervise_route_experiments.py \
  "$RESCENE_DELIVERY_ROOT/specs/plan.json" --deadline-epoch "${trial_deadline:?Set the cutoff first}" \
  > "$RESCENE_DELIVERY_ROOT/launcher.log" 2>&1 </dev/null &
echo "$!" > "$RESCENE_DELIVERY_ROOT/launcher.pid"
```

| 时段 | 顺序与参数 |
|---|---|
| 0–3 小时 | 完成 CUDA、VGGT、PyCOLMAP、gsplat 和 SPZ 冒烟，先跑 100-step，再跑 Golden Kitchen 三路线各一次。确认新策略的限时、锁和归档流程。 |
| 3–10 小时 | 在两个开发场景各跑一轮生产基线。FAST/BALANCED 用 80 帧，QUALITY 用 250 帧，再补一个 160 帧的规模对照。三档沿用 7k / 20k / 20k 步。 |
| 10–18 小时 | 按 QUALITY、BALANCED、FAST 顺序筛选。QUALITY 用同一匹配数据库的独立副本比较全局与增量建图；BALANCED 固定 80 帧和查询点数，将查询帧 8 改为 6；FAST 固定分辨率、7k 步及验证图，将 80 帧改为嵌套的 64 帧。每条路线每个开发场景先跑一对，固定试验变量之外的设置和随机种子。后续配对交替改变对照与候选的运行先后。 |
| 18–28 小时 | 一个候选须在室内、室外开发场景各完成三次有效配对，并在两类独立留出场景各通过一对。同一随机种子配对，三个开发种子预先冻结为 42、43、44，留出用 42。优先做齐一个路线的证据。主计划完成且在第 28 小时前还剩至少 90 分钟，才做 MV-DUSt3R+ 冒烟。 |
| 28–30 小时 | 归档、校验、恢复 Worker。若有测试任务和时间窗口，验证图片与视频各一条真实链路；未完成则留到后续验收并登记状态。 |

预算不足时优先三条基线、一个路线的完整对照及 Worker 恢复。已开始的配对保留结果，证据不足的路线单独标记。记录几何、训练、导出和归档的分阶段耗时，以及读写速率、CPU/RSS、进程树显存和实际写入峰值。

QUALITY 先确认环境锁对应的 `pycolmap.global_mapping` 可用。每个场景和帧档各生成一份匹配数据库，两个 mapper 从各自副本启动，输入帧、相机与 MVS 设置固定。缓存数据库试验只用于建图筛选，晋级所用端到端耗时由双方完整冷启动复测。如果全局建图需要额外的视图图标定，把它作为单独的组合候选，推迟到下一批并单列计时。首批采用现有增量 mapper 作为对照。[PyCOLMAP 官方接口](https://colmap.github.io/pycolmap/pycolmap.html#pycolmap.global_mapping)

## 4. 证据和晋级

- 每次保留输入清单、环境锁、最终配置、阶段日志、指标、判定和逐视图结果。每个场景、路线、帧档和配置保留首个有效基线及最终候选的一份 checkpoint、PLY、SPZ，验证可重载、大小和 SHA-256。归档写入共享盘暂存目录，校验后同挂载点原子改名，再清理本批次登记的本地缓存。
- 试验可通过 `allow_missing_validation: true` 启用 7/8 初筛。缺失视图继续留出，结果保留全部冻结来源、实际渲染来源和稀疏点支撑来源。配对比较使用双方共同渲染且有稀疏点支撑的视图。少于 7 张共有有效视图时登记为样本不足。
- 正式晋级要求 8 张冻结验证图全部有渲染和稀疏点支撑、光度指标有限、注册率较同场景对照最多下降 1 个百分点，并且 GPU 峰值较实测总显存至少留出 3 GiB。光度回退容差为 PSNR −0.20 dB、SSIM −0.01、LPIPS +0.01。注册率以该试验输入为分母，FAST 同时报告在 64 张公共图上的注册率。按场景报告所有尝试的失败与降级、有效配对的中位数和范围。几何质量分别记录 COLMAP 稀疏、稠密及 Gaussian 产物，并使用各自正确的坐标变换。
- FAST 主收益为端到端耗时至少缩短 15%。BALANCED 主收益为 BA 峰值显存至少下降 10%，或端到端耗时至少缩短 15%。BA 前后在共同观测上统计，候选相对基线的重投影误差增加最多 0.10 px。QUALITY 主收益为建图阶段至少缩短 20%、端到端至少缩短 10%，且同一 ETH3D 距离阈值下的稠密点云 F1 相对回退最多 5%。有充分证据时，以开发配对中位数判主收益，两个留出场景均须通过质量、显存和不新增失败的门槛。
- 基线在冻结场景失败时如实报告该组合的可用性，可以记录候选是否恢复。缺少可比的有效对照时，将该组合标为样本不足。候选通过开发组重复、独立留出及导出核验后进入评审，生产默认改动单独提交。

监督器的 `phase_gpu` 提供分阶段利用率均值和采样显存峰值。GPU 忙闲仍由计算进程归属确定。供数对照可在规格中启用 `gsplat_cache_images`，将解码及去畸变后的训练图像预加载到主机内存，配置预算为 2 GiB。跟踪显存对照可设置 `vggt_track_observation_limit`，保留总查询帧数与关键点预算，每次只改变每个批次能容纳的观测数。

## 5. 少视图与长序列后续实验

1. **MV-DUSt3R+** 先锁定官方混合 4–12 视图训练的 `MVDp_s2.pth`，核对权重和数据许可。用独立 Blackwell 兼容环境，首轮只跑 8 张输入的推理、COLMAP 导出、投影校验和 100-step gsplat。官方基线使用 Torch 2.5.1 并在 CUDA 12.4 上测试，RTX 5090 的可运行性以实测为准。[官方仓库](https://github.com/facebookresearch/mvdust3r) · [许可证](https://github.com/facebookresearch/mvdust3r/blob/main/LICENSE)
2. 冒烟通过后，在独立批次做室内、室外的 4、8、12 张输入对照。VGGT 与 MV-DUSt3R+ 同输入、同 gsplat 配置。额外测试视图的 RGB 全程留出，使用标定真值，并通过参与优化的相机估计相似变换将真值相机对齐到重建坐标。若对齐退化或渲染器无法验证这一口径，该场景只比较几何与可用性。检查内参缩放、坐标手性、图像名、相机投影和置信度过滤。少视图结果单列，保留失败样例。
3. 主实验表明 80 帧受显存或覆盖限制时，再用同一长序列检查 VGGT-Long 的分块和回环，评估轨迹漂移、窗口重叠处的误差、显存和端到端耗时。高分辨率 Mip-NeRF 360 另开批次，每次只展开一个场景，首轮不与模型迁移混测。[VGGT-Long](https://github.com/DengKaiCQ/VGGT-Long)

MV-DUSt3R+ 的研究源码锁定到 `5322fcf3acfaad695d4aba1a44563c3a1c8f8979`。发布方记录 `MVDp_s2.pth` 约 7.94 GB，SHA-256 为 `418118dc4c01d18c7420dff6e911b4a4b874dbd244b99f1f5cbd0005f96de97b`。权重与独立环境计入 20 GB runtime 预算。下载后校验实际文件，再在隔离实验环境加载。[官方权重元数据与许可](https://huggingface.co/Zhenggang/MV-DUSt3R/blob/7f4ae79613eb487c5b06b73ef14169903286e0ef/checkpoints/MVDp_s2.pth)

研究进程用 NPZ 交付两端约定的中间格式，包含 `image_names`、`intrinsics`、`cam_from_world`、`points`、`colors`、`image_indices` 和 `pixels`。其中相机外参为世界到相机，内参和观测像素与实际写入 `images/` 的分辨率一致，颜色为 uint8 RGB。使用 `python scripts/export_experimental_geometry.py <predictions.npz> <scene>` 导出 `sparse/0` 并通过 PyCOLMAP 重载。独立真实模型进程仍需在 5090 上验证。

## 1. 当前架构

### 3.2 OSS 与 RAM

当前使用北京地域私有 Bucket `rescene-prod-741277` 和一个 RAM Role `ReSceneOssSessionRole`。API 按调用场景动态附加 STS Session Policy：

1. 浏览器上传凭证只允许操作单个 asset key。
2. Worker 凭证只读当前项目的 `assets/*` 和当前 Job 的已有归档，只写当前 Job 的 `attempts/{attempt}/*`。项目资产前缀避免多图作业超过 STS Policy 大小限制。

API 的长期 AccessKey 只允许 `sts:AssumeRole`，不直接授予 Bucket 读写权限。生产 Bucket CORS 允许 Web `https://app.rescene.xyz` 和 Windows Tauri `http://tauri.localhost`，方法为 `GET, PUT, POST, DELETE, HEAD`，暴露 `ETag`、请求 ID、内容长度和内容类型，缓存 600 秒。

### 4.2 安装文件

源码准备和运行时目录分开：`/opt/rescene` 是原有运行目录；每次将已核对提交的归档解压到一个此前不存在的独立暂存目录，绝不覆盖或清理运行目录。2026-11-11 曾因旧文件混入构建上下文导致失败，见第 14 节。

例如，本机执行 `git archive --format=tar.gz -o /tmp/rescene-src.tar.gz HEAD`，将归档传到服务器后，在服务器上新建空目录 `/root/rescene-stage-<唯一标识>` 并解压到该目录；确认提交和归档内容。不要使用已有目录或包含运行数据的目录作为暂存目录。以下命令中的 `<唯一标识>` 应先替换成实际目录名。

运行目录中的 `infra/.env`、`infra/secrets/`、`infra/postgres/`、`infra/backups/` 和 `releases/` 必须保留，不纳入版本控制；不自动删除或移动未知文件。首次安装另行创建运行目录，参考 `infra/.env.example` 配置环境变量并单独设置 Secret，不要把实际 Secret 写进 `.env`。

构建前先按 §4.3 完成备份，人工对比暂存与运行目录的 Compose 配置及迁移。若配置变化，先审查并安全更新运行配置，确保保留数据库、Secret、备份及网络的原有路径；无法确认时停止。以下构建命令只使用暂存源码，不启动暂存 Compose 中的服务：

```bash
docker compose --project-directory /root/rescene-stage-<唯一标识>/infra \
  --env-file /opt/rescene/infra/.env -f /root/rescene-stage-<唯一标识>/infra/compose.yaml build api web
```

暂存 Compose 的 `context: ..` 因此指向干净源码；运行服务始终使用 `/opt/rescene/infra/compose.yaml` 和 `/opt/rescene/infra` 项目目录，避免相对 bind mount、Secret 和数据库路径指向暂存区。构建默认生成项目 `rescene` 的 `rescene-api`、`rescene-web` 镜像；核对 Compose 项目名及镜像名称，配置不一致时不要切换。容器不映射宿主机端口；Web、API 与现有 Caddy 通过 `rescene` 网络互通。

以下是 0.4.1 首次切换时的历史演练：当时将生产 `0006` 备份隔离升级至 `0009`；后续审计部署已升至 `0010`。原 0.4.0 API 镜像在 `0009` 上启动失败（`Can't locate revision identified by '0009'`），在还原的 `0006` 上启动并通过就绪检查。现网 PostgreSQL `archive_mode=off`，本轮未验证可按时间点恢复。因此不得设置 `RESCENE_COMPAT_VERIFIED=1`，也不能在开放写入后直接还原部署前快照。正式切换前先确认停写窗口：等在途请求与任务完成，停写后才做最终快照；在恢复写入前验证 API、Web 与候选 Worker。开放写入后的异常需前滚修复，或先保全并核对迁移后的写入再恢复。停写时应同时切断公网 API 写入、停止所有旧 API 实例及 Worker 领租约，而不只是屏蔽 Web 按钮。当时备份后逐项验证候选 API 就绪、数据库 `0009`、工作台登录与历史结果可读；后续部署须按实际目标迁移版本重新核验；先用独立队列验证候选 Worker，恢复写入后再启用生产 Worker、观察真实队列。

无 Alembic 版本标记的旧库只有与固定的 `0001` 历史结构一致时才会自动接管并升级；结构不一致时启动拒绝并列出差异，不要手工猜测或写入版本标记。先停止升级，在隔离副本核对数据库来源、结构和恢复方案。生产接管须单独验证。

```bash

(umask 077; docker compose --project-directory /opt/rescene/infra --env-file /opt/rescene/infra/.env \
  -f /opt/rescene/infra/compose.yaml exec -T db \

docker inspect --format '{{.Name}} {{.Image}}' rescene-api rescene-web rescene-db \
```

备份、恢复演练和 §4.2 的干净构建成功后，检查运行配置，再只切换 API：

```bash
docker compose --project-directory /opt/rescene/infra --env-file /opt/rescene/infra/.env \
  -f /opt/rescene/infra/compose.yaml config --quiet
```

```bash

  -f /opt/rescene/infra/compose.yaml up -d --no-deps --no-build web
```

确认 Web 容器健康、站点响应以及其他服务正常。`--no-deps` 避免连带重建数据库，`--no-build` 使用已构建镜像。部署成功后将镜像 ID、摘要、配置版本及验收结果记录到 `releases/<版本>/`；保留现有发布记录，不自动删除传输包或其他文件。回滚见 §7。

`scripts/deploy_targeted.sh <版本> <ssh-host> <remote-root>` 把上述人工步骤串成一次运行，并按 `prepare`、`transfer`、`load`、`api`、`web`、`verify` 六个阶段记录到 `.cache/release/<版本>/phases.log` 和远端 `releases/<版本>/status.txt`。镜像装载成功后才改 `rescene-api:latest`；API 健康后改 `rescene-web:latest`；两段都通过后才做公网探测。中断时输出停在哪一阶段、本次改过哪些服务以及 `before-images.txt` 路径。是否自动恢复旧镜像由 `RESCENE_COMPAT_VERIFIED=1` 决定：未设置时脚本只报告状态并非零退出，因为旧镜像对新 schema 的兼容需要人工确认。

脚本在切换前把快照写入 `infra/backups/rescene-pre-deploy-<版本>-<UTC时间戳>.dump`，实际路径同时记录到 `releases/<版本>/pre-deploy-dump.txt`。快照使用 `umask 077` 写临时文件，经 `pg_restore --list` 验证后以 `root:65532`、`0640` 原子发布；目录为 `0750`。文件名匹配每日备份的 `rescene-*.dump` 规则，因此会随 14 天保留期清理，并可能被周日上传任务选中。历史遗留的 `pre-deploy-*.dump` 不会自动删除；先列目录人工确认，至少执行 `chmod 600` 收紧权限，再决定移走或归档。

本机不再手工传输镜像：`release.yml` 的 `deploy` job 在主机上直接按 tag 源码重建两个镜像，执行同样的备份、逐服务切换和公网探测，并把过程写入 `deploy-log.json`。上文的人工步骤和 `deploy_targeted.sh` 保留为无 CI 时的回退手段，见 §16。

### 4.4 Caddy 安全接入

1. 确认 DNS 已生效。
2. 备份 `/root/docker/caddy/conf/Caddyfile`。
3. 确认 Caddy 版本不低于 2.10.0：API 块的 `request_body { max_size 2MB }` 是 v2.10.0 起的实验指令，旧版本会在 `caddy validate` 阶段拒绝。
4. 将 `infra/caddy/rescene.caddy` 的两个站点块追加到 Caddyfile。
5. 将现有 Caddy 容器接入 `rescene` 网络。
6. 在容器内执行 `caddy validate`。
7. 仅在校验成功后 graceful reload。
8. 检查全部既有域名和两个 ReScene 子域名，并确认响应头：
   - `app.rescene.xyz`：`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、HSTS 和含 `frame-ancestors 'none'` 的 CSP。
   - `api.rescene.xyz`：`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、HSTS。
   - API 块的 `header_up X-Real-IP {http.request.client_ip}` 覆盖客户端自带值；`{http.request.client_ip}` 会按 `trusted_proxies` 解析 Cloudflare 头，而 `{remote_host}` 只是 Cloudflare 边缘地址。API 只接受经 Caddy 的流量，不得直接暴露端口。

工作台 CSP 的 `script-src` 第一阶段保留 `'unsafe-inline'`（Next.js 内联 bootstrap）和 `'wasm-unsafe-eval'`（hash-wasm），并允许 API、OSS 媒体和 `blob:` worker。后续在 `apps/web` 加入 nonce 后再移除 `'unsafe-inline'`。CSP 误伤 OSS 媒体时应先在隔离域名用 `Content-Security-Policy-Report-Only` 观察，不要直接照搬官网静态站的 `default-src 'none'`。

HSTS 当前只设 `max-age=31536000`；确认所有 `*.rescene.xyz` 子域都强制 HTTPS 后再追加 `includeSubDomains`，避免把未知子域锁死在 HTTPS。

`scripts/deploy_targeted.sh` 的 `verify` 阶段会断言上述响应头；因此 Caddy 变更必须先于定向部署上线，否则部署会以失败结束并进入回滚流程。

任何一步失败都恢复 Caddyfile 备份并 reload。禁止批量重启容器、修改 FRP 或执行 `docker system prune`。

## 5. RTX 5090 部署

代码目录为 `/root/ReScene`，大文件目录为 `/root/autodl-tmp/rescene`。Python、缓存和工具通过符号链接落到 50 GB 数据盘。从 Git 归档暂存候选时，先在候选目录运行 `chmod 0755 workerctl scripts/workerctl`；两个入口在归档中为 `0644`，务必保留生产目录和已有锁。

后续大场景实验的归档放在 `/root/autodl-fs/rescene`，训练时逐场景同步到本地数据盘。共享盘的 200 GB 账户上限、ReScene 150 GB 预算和开机后的实验顺序见 [5090 大数据集训练运行手册](5090大数据集训练运行手册.md)。

```bash
cd /root/ReScene
cp worker.env.example worker.env
mkdir -p secrets
chmod 700 secrets
# 写入与 API 相同的 Worker Token，随后 chmod 600 secrets/worker_token
./workerctl bootstrap
./workerctl smoke
./workerctl start
./workerctl status
```

`worker.env` 的 API 地址已经是 `https://api.rescene.xyz`。Worker 使用 `nohup + setsid + flock + PID file`；SSH 断开不会终止任务。启动层通过 `taskset 0-11` 将 Worker 及全部子进程硬限制在 12 个 CPU 核，同时设置 OMP/MKL/OpenBLAS/NumExpr 线程上限。发现其他 GPU compute PID 时只等待，不会杀进程，也不依据虚假的 `utilization.gpu=100%` 判断忙闲。

API/STS 调用包含有界重试；恢复凭证可读取当前 Job 的 checkpoint，但不能读取其他 Job。恢复时不会重复压缩已作为恢复来源的阶段，避免大目录归档阻塞 heartbeat。

维护前执行：

```bash
./workerctl drain
./workerctl status
./workerctl stop
```

`drain` 只阻止领取新任务，当前 Job 会继续。取消 Job 时 Worker 只终止登记的任务进程组。清理路径必须位于 `/root/autodl-tmp/rescene/jobs/{job_id}`。

## 7. 回滚

不要执行全栈 `down`，也不要删除 PostgreSQL 数据目录。先确认旧 API 与当前数据库迁移版本、数据及 Worker 租约协议兼容；仅新增表或列不足以证明兼容。先在隔离环境验证。不兼容或尚未验证时停止，制定并演练数据库恢复方案，评估恢复备份会丢失备份后的写入，再安排维护窗口；不得直接覆盖生产数据库。

需要找回部署前快照时，先读 `releases/<版本>/pre-deploy-dump.txt`；没有该记录时用 `ls -1t /opt/rescene/infra/backups/rescene-pre-deploy-*.dump` 列出候选。旧版本的 `pre-deploy-*.dump` 只作历史材料，不要与新快照混用；任何恢复前都先对隔离数据库执行 `pg_restore --list` 和实际恢复演练。

确认兼容后，从部署前 `before-images.txt` 核实旧 API 和 Web 镜像 ID 均存在，结合旧运行配置核对镜像标签。将旧 ID 分别标记为 `rescene-api:latest`、`rescene-web:latest` 后，用运行目录的 Compose 定向切换，先 API：

```bash
docker compose --project-directory /opt/rescene/infra --env-file /opt/rescene/infra/.env \
  -f /opt/rescene/infra/compose.yaml up -d --no-deps --no-build api
```

确认 API 健康且 `/health/ready` 成功，再用相同命令将末尾 `api` 改成 `web`；确认 Web 健康和站点响应。若 Caddy 配置也曾变更，单独校验后恢复相应备份并 graceful reload；不改动其他站点。Worker 版本或租约协议不兼容时，按维护流程先 drain 并协调 Worker，不能只回退 API。

状态未知时不要重跑定向部署脚本。脚本只恢复本次实际改过的服务，顺序为 web、api；兼容未确认、恢复失败或 SSH 断线时保留原错误并非零退出，不做部分覆盖。先读 `releases/<版本>/status.txt`、`phases.log`、`before-images.txt`，用 `docker inspect` 核对当前镜像 ID，人工判断停在 `api` 还是 `web`，再按本节命令逐项切换。只有确认旧镜像对当前 schema 兼容后才设置 `RESCENE_COMPAT_VERIFIED=1` 重跑，否则先制定数据库恢复方案。

## GPU 维护与长任务监督

实验前先 drain；使用与 Worker 相同的 `.gpu.lock` 等待活动 Job 正常结束，再 stop。队列中的任务保留。外部 compute PID 存在时不得启动实验，也不得杀该进程。

维护脚本若在退出清理中重启 Worker，外层锁必须使用 `flock --close -w 60 /root/ReScene/.gpu.lock bash <维护脚本>`：锁由 flock 父进程持有，不将锁描述符传给脚本或新 Worker。本轮已观察到未使用 `--close` 时，重启的 Worker 继承 `.gpu.lock`，后续验证一直等锁且 GPU 空闲。不能用两小时等待上限掩盖这个死锁。

长任务每 15 秒输出阶段状态、各阶段日志大小、GPU 显存/利用率与无进展时长。180 秒无阶段/日志进展先告警；连续 900 秒无进展且 GPU 空闲，或超过该诊断的总时限，才终止本次拥有的进程组并执行源恢复和 Worker 恢复。不能仅凭 GPU 利用率为 0 判卡死，预处理、下载、编译和导出可能不使用 GPU。监督日志与失败证据保留；重新启动必须使用新试验标识或明确的恢复协议，不能覆盖旧实验。

恢复后先核对 Worker status、drain、heartbeat 和锁可用性，再跑真实小型 Job；CUDA smoke 不等于业务恢复。

### 11.2 API 增量

- `POST /v1/projects/{id}/assets/upload-session` 与 `POST /v1/assets/{id}/upload-session?mode=post` 返回 `mode` 字段。`post` 模式返回签名后的 `url` 与 `fields`（key、policy、OSSAccessKeyId、signature、success_action_status），策略只允许写单个对象键，1 小时过期，单对象上限 5 GiB。
- `POST /v1/auth/register` 用邮箱 + 密码（至少 12 位）开放自助注册，成功即返回访问令牌；同邮箱再次注册返回 409。`POST /v1/auth/login` 查询前对邮箱做去空格与小写归一化。
- `RESCENE_CORS_ORIGINS` 默认放行 Web 3000、Expo 8081、Vite 1420 与 Tauri 的 `http://tauri.localhost`。生产按实际域名覆盖。
- 所有上传仍以 `POST /v1/assets/{id}/complete` 的 HEAD 校验和 SHA-256 比对作为唯一置 READY 的入口。

### 11.3 小程序与移动端限制

- 小程序单文件最多 10 MiB，每次最多选 8 个文件。当前 AppID 使用个人主体，客户端通过 HTTPS 链接在手机浏览器打开 Viewer。
- 小程序无 `fetch`，`apps/miniapp/src/polyfill.ts` 把 `Taro.request` 适配到客户端读取的最小集合；因此小程序走轮询而非 SSE。
- 桌面端把 SPZ 缓存在 app cache 目录（`cache_artifact` 命令，仅 https，原子重命名），二次打开不再下载；失败时回退到 CDN 地址。

### 12.3 标定驱动

```bash
scripts/route_calibration.sh all   # wait -> baseline -> screen -> select -> validate -> holdout -> finalize -> evaluate
```

每个阶段都可单独重跑（`wait|screen|select|validate|holdout|evaluate|finalize`），基准阶段统一带 `--resume`，中断后继续未完成的 trial。脚本先等 `rescene benchmark` 进程退出、`nvidia-smi` 无 compute PID 再开跑，避免和生产任务抢 GPU。产物：

| 阶段 | 输出 |
|---|---|
| screen | `calibration/route-screen-v2/leaderboard.json` |
| select | `calibration/selection-v2-screen.json`、`configs/calibration/route-winners-v2.json` |
| validate | `calibration/route-validation-v2/leaderboard.json` |
| holdout | `calibration/route-holdout-v2/leaderboard.json` |
| evaluate | `calibration/route-holdout-v2/official.json` |
| finalize | `calibration/selection-v2.json`、`configs/calibration/selected-v2.json` |

`selected-v2.json` 与候选文件同构，可以直接当作 `--candidates` 复跑。晋级规则在 `src/rescene/selection.py`：render 项必须在屏幕集上达到速度上限且不劣于基线，validation 要求至少两个场景有改进，holdout 只要求不劣化。

### 12.4 holdout 官方评测

```bash

  --leaderboard calibration/route-holdout-v2/leaderboard.json \
  --evaluator .cache/multi-view-evaluation/build/ETH3DMultiViewEvaluation \
  --output calibration/route-holdout-v2/official.json
```

脚本把每个 holdout run 的点云按位姿相似变换对齐到扫描坐标系，再调用官方程序按 0.02 m 容差取 accuracy/completeness/F1。场景若带 `dslr_calibration_undistorted` 就用其中的 COLMAP 位姿求变换；缺失时退回原始坐标系（ETH3D 的参考扫描本就注册在去畸变相机系）。

### 15.3 失败与恢复

激活、自动验收和回滚在同一远端 Bash 事务中完成。仅恢复本次事务切换且仍由其拥有的片段和链接；首次发布没有旧链接时只删除本次创建的链接。恢复后 validate、graceful reload 并核对原服务，确认后记录 `rolled_back`，命令仍非零退出。第三方修改、恢复失败或原服务不符时记录 `recovery_unconfirmed`（恢复未确认），保留备份与正在运行的 Caddy，不覆盖他人修改。

SSH 断线后脚本只查询原事务并等待锁，最多 240 秒，不再次切换。检查返回的事务 ID、阶段、配置哈希和 current 目标；只有 `committed` 且现状一致才认定成功。出现“恢复未确认”时先读取对应记录和备份，人工核对每个对象的所有权后恢复，禁止盲目重跑或重启整栈。正常回退到旧官网版本可用同一脚本发布已有成功 CI 的旧提交，旧共享资源继续保留；这不是 API/Worker 降级。

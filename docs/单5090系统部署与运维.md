# ReScene 单 RTX 5090 系统部署与运维

## 1. 当前架构

ReScene 使用 `rescene.xyz` 的两个子域名：

- `app.rescene.xyz`：Next.js 团队工作台和 SPZ Viewer。
- `api.rescene.xyz`：FastAPI、任务队列、STS 和 Worker API。

公网服务器只承载 Web、API 和独立 PostgreSQL；素材和重建产物由浏览器或 GPU Worker 直接读写阿里云 OSS。AutoDL RTX 5090 不监听公网端口，只主动访问 API 与 OSS。队列只允许一个 GPU Job 运行。

## 2. 已实现组件

| 组件 | 位置 | 说明 |
|---|---|---|
| 三条重建路线 | `src/rescene` | FAST、BALANCED、QUALITY；保留 resume、GPU 锁和一次 OOM 降级 |
| Job 入口 | `python -m rescene run-job` | 接收本地 `job.json`，输出到 Worker 指定目录 |
| API | `src/rescene_api` | 团队鉴权、项目、素材、任务、租约、重建、分享和审计 |
| Worker | `src/rescene_worker` | 主动领任务、OSS 传输、心跳、取消、阶段归档与安全清理 |
| Web | `apps/web` | 登录、项目、直传、Profile、进度、GPU 状态和 SPZ Viewer |
| 公网部署 | `infra/compose.yaml` | 独立 Compose、资源上限、健康检查、PostgreSQL 和备份工具 |
| 5090 管理 | `scripts/workerctl` | bootstrap、start、drain、stop、status、logs、smoke |

### 3.1 DNS

| 主机记录 | 类型 | 值 |
|---|---|---|
| `app` | A | `107.151.246.42` |

等待公共 DNS 能解析后再加载 Caddy 配置。不要先加载配置反复申请失败的证书。

### 3.2 OSS 与 RAM

当前使用北京地域私有 Bucket `rescene-prod-741277` 和一个 RAM Role `ReSceneOssSessionRole`。API 按调用场景动态附加 STS Session Policy：

1. 浏览器上传凭证只允许操作单个 asset key。
2. Worker 凭证只读当前项目的 `assets/*` 和当前 Job 的已有归档，只写当前 Job 的 `attempts/{attempt}/*`。项目资产前缀避免多图作业超过 STS Policy 大小限制。

API 的长期 AccessKey 只允许 `sts:AssumeRole`，不直接授予 Bucket 读写权限。Bucket CORS 已限制来源为 `https://app.rescene.xyz`，方法为 `GET, PUT, POST, DELETE, HEAD`，暴露 `ETag`、请求 ID、内容长度和内容类型，缓存 600 秒。

### 3.3 凭据

当前 5090 已验证密钥登录，实例 sshd 已关闭密码认证。切换时已轮换 Worker Token。AutoDL 控制台中保留的旧密码和废弃实例仍由账户所有者管理。

不得提交 `infra/.env`、`infra/secrets/*`、`worker.env`。在公网服务器创建：

```text
/opt/rescene/infra/secrets/db_password
/opt/rescene/infra/secrets/jwt_secret
/opt/rescene/infra/secrets/worker_token
/opt/rescene/infra/secrets/admin_password
/opt/rescene/infra/secrets/oss_access_key_secret
```

Secret 目录权限为 `0700`。仅宿主机使用的文件保持 `0600`；需要由 UID/GID 65532 的 API 容器读取的 bind-mounted Secret 使用 `root:65532`、`0640`。`jwt_secret` 和 `worker_token` 至少使用 32 字节随机值，初始管理员密码至少 12 个字符。公网 API 与 GPU Worker 的 `worker_token` 必须完全一致。

### 4.1 前置检查

公网服务器地址为 `107.151.246.42`，本地用 `~/.ssh/config` 里的 `soloeternity-root` 别名登录（密钥 `id_ed25519_soloeternity`）。旧配置里的 `aliyun` 别名指向已停用实例，连接会在 SSH 握手阶段被关闭，不要使用。

```bash
free -h
df -h /
docker ps --format '{{.Names}}\t{{.Status}}'
docker network inspect rescene >/dev/null 2>&1 || true
```

部署前记录现有 17 个容器、站点响应和可用内存。创建 2 GiB Swap，设置 `vm.swappiness=10`；完成后再次确认现有服务没有延迟异常。

### 4.2 安装文件

`/opt/rescene` 只放仓库 HEAD 的内容，加上运行数据。同步时用 `git archive` 打包已提交的文件，并**先清掉工作目录里的旧文件再解包**：

```bash
# 本机
git archive --format=tar.gz -o /tmp/rescene-src.tar.gz HEAD
scp /tmp/rescene-src.tar.gz <host>:/root/rescene-src.tar.gz
# 服务器
cd /opt/rescene
find . -mindepth 1 -maxdepth 1 ! -name infra ! -name releases -exec rm -rf {} +
find infra -mindepth 1 -maxdepth 1 ! -name .env ! -name secrets ! -name postgres ! -name backups -exec rm -rf {} +
tar xzf /root/rescene-src.tar.gz -C .
# 校验目录与 HEAD 一致
rm -rf /tmp/headcheck && mkdir -p /tmp/headcheck && tar xzf /root/rescene-src.tar.gz -C /tmp/headcheck
diff -rq /tmp/headcheck /opt/rescene --exclude=infra --exclude=releases
```

只解包不清理会留下旧版本仍存在的文件。2026-11-11 的 0.3.0 部署就因此把 0.1.0 的 `apps/web/components/Viewer.tsx` 一起带进了构建上下文，`next build` 编译这个陈旧文件后报 `TS2307: Cannot find module 'three'`；清理目录后同一提交构建通过。

解包覆盖不到以下运行数据，禁止删除或纳入版本控制：

- `infra/.env`、`infra/secrets/`（权限 0700 / 0600 / `root:65532` 0640）
- `infra/postgres/`（数据库数据目录）
- `infra/backups/`（部署前 dump 与每日备份）
- `releases/`（每次部署的镜像记录）

旧版本遗留的临时文件（`*.tar`、`*-rollback-*`、构建日志）应移出工作目录，例如 `mv <file> /root/rescene-old-$(date +%Y%m%d-%H%M%S)/`，不要 `rm -rf` 整个目录。

首次安装时复制 `infra/.env.example` 为 `infra/.env` 并填入 OSS/RAM 参数。不要把实际 Secret 写进 `.env`。

```bash
cd /opt/rescene
docker compose --env-file infra/.env -f infra/compose.yaml config --quiet
docker compose --env-file infra/.env -f infra/compose.yaml build api web
docker compose --env-file infra/.env -f infra/compose.yaml ps
```

容器不映射宿主机端口。`rescene-web`、`rescene-api` 与现有 Caddy 通过名为 `rescene` 的 Docker 网络互通。

### 4.3 版本升级

升级只重建并替换 `api`、`web` 两个容器，数据库容器保持运行；`api` 启动时执行 `alembic upgrade head`，迁移随镜像生效。

```bash
cd /opt/rescene
ts=$(date +%Y%m%d-%H%M%S); mkdir -p /root/rescene-backup-$ts
cp -a infra/.env infra/compose.yaml /root/rescene-backup-$ts/
docker compose --env-file infra/.env -f infra/compose.yaml exec -T db \
  pg_dump -U rescene -Fc rescene > infra/backups/pre-deploy-$(cat VERSION).dump
test -s infra/backups/pre-deploy-$(cat VERSION).dump
docker inspect --format '{{.Name}} {{.Image}}' rescene-api rescene-web rescene-db \
  | tee /root/rescene-backup-$ts/before-images.txt
docker compose --env-file infra/.env -f infra/compose.yaml build api web
docker compose --env-file infra/.env -f infra/compose.yaml up -d --no-deps api
docker compose --env-file infra/.env -f infra/compose.yaml ps api
docker compose --env-file infra/.env -f infra/compose.yaml up -d --no-deps web
docker compose --env-file infra/.env -f infra/compose.yaml ps web
```

`--no-deps` 保证不会连带重建数据库。API 就绪后再替换 Web，避免前端指向未升级的接口。回滚时用 `before-images.txt` 里的镜像 ID 重新 `docker tag` 成 `rescene-api`/`rescene-web` 并再次 `up -d --no-deps`。

部署成功后把 `docker inspect` 输出和镜像摘要写入 `releases/<版本>/`，格式与 `releases/0.2.1/` 一致；同时清理该版本之前残留的 `images.tar.gz`（镜像已在宿主机上，tar 包只用于跨机传输）。

### 4.4 Caddy 安全接入

1. 确认 DNS 已生效。
2. 备份 `/root/docker/caddy/conf/Caddyfile`。
3. 将 `infra/caddy/rescene.caddy` 的两个站点块追加到 Caddyfile。
4. 将现有 Caddy 容器接入 `rescene` 网络。
5. 在容器内执行 `caddy validate`。
6. 仅在校验成功后 graceful reload。
7. 检查全部既有域名和两个 ReScene 子域名。

任何一步失败都恢复 Caddyfile 备份并 reload。禁止批量重启容器、修改 FRP 或执行 `docker system prune`。

### 4.5 备份

手工验证：

```bash
docker compose --env-file infra/.env -f infra/compose.yaml --profile tools run --rm backup
```

确认生成的 dump 能恢复到一个临时 PostgreSQL 后，再由 root cron 每日执行。当前日备份在每天 03:17 执行并保留 14 天；周日 03:47 将最新 dump 上传到 OSS 的 `projects/system/backups/postgresql/weekly/`，Bucket 生命周期保留 8 周。

## 5. RTX 5090 部署

代码目录为 `/root/ReScene`，大文件目录为 `/root/autodl-tmp/rescene`。Python、缓存和工具通过符号链接落到 50 GB 数据盘。

```bash
cd /root/ReScene
cp worker.env.example worker.env
mkdir -p secrets
chmod 700 secrets
# 写入与 API 相同的 Worker Token，随后 chmod 600 secrets/worker_token
./workerctl bootstrap
./workerctl smoke
./workerctl start
./workerctl status
```

`worker.env` 的 API 地址已经是 `https://api.rescene.xyz`。Worker 使用 `nohup + setsid + flock + PID file`；SSH 断开不会终止任务。启动层通过 `taskset 0-11` 将 Worker 及全部子进程硬限制在 12 个 CPU 核，同时设置 OMP/MKL/OpenBLAS/NumExpr 线程上限。发现其他 GPU compute PID 时只等待，不会杀进程，也不依据虚假的 `utilization.gpu=100%` 判断忙闲。

API/STS 调用包含有界重试；恢复凭证可读取当前 Job 的 checkpoint，但不能读取其他 Job。恢复时不会重复压缩已作为恢复来源的阶段，避免大目录归档阻塞 heartbeat。

维护前执行：

```bash
./workerctl drain
./workerctl status
./workerctl stop
```

`drain` 只阻止领取新任务，当前 Job 会继续。取消 Job 时 Worker 只终止登记的任务进程组。清理路径必须位于 `/root/autodl-tmp/rescene/jobs/{job_id}`。

## 6. 验收顺序

1. `curl https://api.rescene.xyz/health/live` 和 `/health/ready`。
2. 管理员登录、创建项目、上传两张测试图片。
3. GPU 关机时创建 Job，确认状态保持 `QUEUED` 且 UI 显示 Worker 离线。
4. 开机并启动 Worker，完成 100-step smoke。
5. 依次运行 FAST、BALANCED、QUALITY Golden Case。
6. 验证 checkpoint、PLY、SPZ、metrics、report 和 manifest 均在 OSS。
7. 在浏览器打开 SPZ，下载 PLY/SPZ，并验证可撤销分享。
8. 杀死 Worker，等待 90 秒租约过期并确认 Job 重新排队。
9. 重新启动 Worker，验证从 OSS 阶段归档恢复。
10. 断开 SSH、取消任务、模拟 OSS 暂时不可用并验证错误状态。
11. 确认公网服务器 available memory 不低于 2 GiB，既有容器和域名正常。
12. 质量标定复跑：`bash scripts/route_calibration.sh wait` 后执行 `all`，按 [5090 质量标定](5090_QUALITY_CALIBRATION.md) 的规则复核 `calibration/selection-v2.json`；晋级后同步 `PROFILES` 并重启 Worker。

## GPU 维护与长任务监督

实验前先 drain；使用与 Worker 相同的 `.gpu.lock` 等待活动 Job 正常结束，再 stop。队列中的任务保留。外部 compute PID 存在时不得启动实验，也不得杀该进程。

维护脚本若在退出清理中重启 Worker，外层锁必须使用 `flock --close -w 60 /root/ReScene/.gpu.lock bash <维护脚本>`：锁由 flock 父进程持有，不将锁描述符传给脚本或新 Worker。本轮已观察到未使用 `--close` 时，重启的 Worker 继承 `.gpu.lock`，后续验证一直等锁且 GPU 空闲。不能用两小时等待上限掩盖这个死锁。

长任务每 15 秒输出阶段状态、各阶段日志大小、GPU 显存/利用率与无进展时长。180 秒无阶段/日志进展先告警；连续 900 秒无进展且 GPU 空闲，或超过该诊断的总时限，才终止本次拥有的进程组并执行源恢复和 Worker 恢复。不能仅凭 GPU 利用率为 0 判卡死，预处理、下载、编译和导出可能不使用 GPU。监督日志与失败证据保留；重新启动必须使用新试验标识或明确的恢复协议，不能覆盖旧实验。

恢复后先核对 Worker status、drain、heartbeat 和锁可用性，再跑真实小型 Job；CUDA smoke 不等于业务恢复。

### 11.1 仓库结构

Web、桌面、移动端和小程序共用 TypeScript 契约与 UI 内核，算法引擎仍是 Python：

| 路径 | 内容 |
|---|---|
| `packages/schemas` | Zod 契约，逐字段对应 FastAPI 响应 |

### 11.2 API 增量

- `POST /v1/projects/{id}/assets/upload-session` 与 `POST /v1/assets/{id}/upload-session?mode=post` 返回 `mode` 字段。`post` 模式返回签名后的 `url` 与 `fields`（key、policy、OSSAccessKeyId、signature、success_action_status），策略只允许写单个对象键，1 小时过期，单对象上限 5 GiB。
- `POST /v1/auth/register` 用邮箱 + 密码（至少 12 位）开放自助注册，成功即返回访问令牌；同邮箱再次注册返回 409。`POST /v1/auth/login` 查询前对邮箱做去空格与小写归一化。
- `RESCENE_CORS_ORIGINS` 默认放行 Web 3000、Expo 8081、Vite 1420 与 Tauri 的 `http://tauri.localhost`。生产按实际域名覆盖。
- 所有上传仍以 `POST /v1/assets/{id}/complete` 的 HEAD 校验和 SHA-256 比对作为唯一置 READY 的入口。

### 11.3 小程序与移动端限制

- 小程序单文件 10 MB、单次 8 个文件，超限在前端过滤；`web-view` 需要在微信后台把 Web 域名加入业务域名。
- 小程序无 `fetch`，`apps/miniapp/src/polyfill.ts` 把 `Taro.request` 适配到客户端读取的最小集合；因此小程序走轮询而非 SSE。
- 桌面端把 SPZ 缓存在 app cache 目录（`cache_artifact` 命令，仅 https，原子重命名），二次打开不再下载；失败时回退到 CDN 地址。

### 12.4 holdout 官方评测

  --leaderboard calibration/route-holdout-v2/leaderboard.json \
